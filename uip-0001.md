# Abstract

This document defines the purpose, format, ownership, lifecycle, and maintenance process for Utocoin Improvement Proposals (UIPs).

# Motivation

Protocol and application changes need a durable specification that is independent of any one implementation. A public proposal process makes design decisions, compatibility constraints, test vectors, and deployment status reviewable by all implementers.

The term UIP distinguishes proposals maintained by the Utocoin project from Bitcoin Improvement Proposals maintained in the `bitcoin/bips` repository.

# Fundamentals

A UIP is a technical document owned by its authors. It may specify consensus rules, peer services, APIs, application-level interoperability, or project processes. Acceptance into this repository means that the document is in scope and meets the repository's editorial requirements. It does not mean that the proposal has community consensus or has been deployed.

The normative specification is the UIP text and its normative auxiliary files. An implementation may be cited as evidence and as a useful reference, but implementation behavior does not silently amend a UIP.

# Proposal Types

- **Specification** defines rules that independent implementations can follow to interoperate.
- **Informational** records guidance, analysis, or design information without imposing interoperability requirements.
- **Process** defines procedures surrounding UIPs or Utocoin project coordination.

# Layers

A UIP preamble identifies its primary layer:

- `Consensus (soft fork)`
- `Consensus (hard fork)`
- `Peer Services`
- `API/RPC`
- `Applications`
- `Process`

# Document Format

UIPs use Markdown and begin with an RFC 822-style preamble in a fenced block. The required fields are:

```text
UIP: <number, or ? before assignment>
Layer: <layer>
Title: <title>
Authors: <authors>
Status: <Draft | Complete | Deployed | Closed>
Type: <Specification | Informational | Process>
Assigned: <YYYY-MM-DD, or ?>
License: <SPDX expression>
Version: <semantic version>
```

Optional fields include `Discussion`, `Requires`, `Replaces`, and `Proposed-Replacement`.

Specification UIPs must define syntax and semantics precisely enough for an independent interoperable implementation. Where applicable, they must define serialization, byte order, size limits, error behavior, resource accounting, compatibility, security assumptions, reference implementations, and deterministic test vectors.

# Number Assignment

Authors submit new proposals using `UIP: ?`, `Assigned: ?`, and a descriptive filename. Authors do not reserve or assign numbers. A UIP editor assigns a number once the proposal is sufficiently complete, in scope, and ready for durable public review.

UIP-1 through UIP-3 are bootstrap assignments made when this repository was established.

# Auxiliary Files

The normative document for UIP `N` is named `uip-NNNN.md`. Auxiliary files are stored in `uip-NNNN/`. Auxiliary material may include machine-readable vectors, reference code, diagrams, schemas, or extended examples.

Normative and non-normative auxiliary material must be clearly labeled. A test-vector generator must produce deterministic output. Test vectors for hashes must include known-answer cases generated independently from the consensus implementation whenever practical.

# Workflow

## Draft

A Draft is under active design and review. Its behavior may change incompatibly. Draft versions use `0.x.y`.

## Complete

A Complete UIP is considered stable by its authors and recommended for adoption. A Specification UIP may become Complete only when its planned specification, reference implementation, and test vectors are available. Version `1.0.0` marks initial completion.

## Deployed

A Complete UIP may become Deployed when there is public evidence that it is active in the intended environment. For a consensus UIP, this requires activation of the specified rules on the relevant production network. A merge into an implementation repository is not sufficient by itself.

## Closed

A UIP becomes Closed when it is abandoned, superseded, or no longer used. Closed documents remain in the repository as historical records.

# Versioning and Changelog

After a UIP becomes Complete, noteworthy changes must be recorded in its Changelog. Breaking changes increment the major version, backward-compatible specification additions increment the minor version, and clarifications or test-vector corrections increment the patch version.

Large breaking changes should normally be proposed as a new UIP rather than silently redefining an established protocol.

# Editors and Ownership

Authors maintain the technical content and respond to substantive review. Editors assign numbers, check formatting and scope, maintain the index, and apply status changes supported by the documented process. Editors do not determine whether a technical proposal is economically desirable or has ecosystem consensus.

Authorship may be transferred or deputies may be added with a public record of the change.

# External Specifications

A UIP may incorporate an external standard by reference. Consensus-critical references must identify an immutable revision or version. The UIP must still summarize the adopted behavior, state every local deviation, and provide local conformance vectors for behavior that differs from the external standard.

Bitcoin BIP numbers remain in the Bitcoin namespace. A reference to Bitcoin BIP 348 does not create or reserve UIP-348.

# Licensing

Each UIP declares an SPDX license expression in its preamble and includes a matching Copyright section. Only licenses that permit free implementation, modification, and redistribution are accepted.
