# Abstract

This proposal defines canonical Taproot script templates for collateralized off-chain payment claims. A payer creates a Stake output and a Payment output. The payer can authorize a recipient using an off-chain claim, and both parties authorize the eventual Payment spend. If the payer signs conflicting claims for distinct recipients, the first recipient can use the two claims to slash the Stake output. The slash transaction fixes a burn output while leaving later outputs available for reporter compensation and fees.

The proposal does not add consensus transaction types. It standardizes byte-exact scripts, claim serialization, Taproot construction, and witness ordering so independent applications can construct and recognize the same contracts.

# Motivation

UIP-2 provides general Script primitives but does not define how wallets exchange identifiers, build claim messages, or construct compatible Taproot trees. Without canonical templates, semantically similar implementations may produce different leaf hashes, output keys, control blocks, and witness layouts.

This proposal defines one interoperable version while preserving application choice over collateral amount, payment amount, expiry, and risk thresholds.

# Scope

This proposal standardizes:

- fixed-width identifiers and claim messages;
- the Payment Tapscript leaf;
- the Stake expiry and slash leaves;
- a standard no-known-private-key Taproot internal key;
- the canonical Taproot tree topology;
- witness element ordering;
- the burn-output commitment used by a slash transaction;
- the information a recipient must independently verify.

Transport protocols, service discovery, user interfaces, fee estimation, and acceptable collateral ratios are outside scope.

# Specification

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

## Version

The templates in this document are version 1. An application identifying these templates outside Script SHOULD use the identifier `uip-3/v1`.

No version field is inserted into the on-chain scripts or signed claim message in version 1. An incompatible template change requires a new UIP-3 major version and different scripts.

## Fixed-width values

| Name | Size | Meaning |
|---|---:|---|
| `AlicePubKey` | 32 bytes | BIP 340 x-only public key used by the payer |
| `StakeSID` | 32 bytes | Identifier bound to one Stake template |
| `SID2` | 32 bytes | Identifier carried by the second conflicting claim |
| `PID` | 32 bytes | Identifier bound to one Payment template |
| `U1` | 32 bytes | First recipient BIP 340 x-only public key |
| `U2` | 32 bytes | Second recipient BIP 340 x-only public key |
| `ClaimSig` | 64 bytes | BIP 340 signature over a claim message |
| `BurnOutputHash` | 32 bytes | UIP-2 `OP_OUTPUTHASH` digest of the burn output |

`StakeSID` and `PID` MUST be generated with at least 128 bits of entropy and SHOULD be uniformly random 32-byte values. They MUST NOT be reused for unrelated logical contracts.

## Claim serialization

A claim message is exactly 96 bytes:

```text
ClaimMessage = SID || PID || UserPubKey
```

There are no CompactSize prefixes, separators, textual encodings, or implicit byte-order transformations. Each component is exactly 32 bytes.

Version 1 contains no signed domain tag. `AlicePubKey` therefore MUST be a key dedicated to UIP-3 version 1 claims and transactions. It MUST NOT be reused to sign arbitrary 96-byte messages in another protocol.

A claim signature is:

```text
ClaimSig = BIP340_Sign(AliceSecretKey, ClaimMessage)
```

The signature is verified directly over the 96-byte message by `OP_CHECKSIGFROMSTACK`.

## Script serialization rules

Conforming implementations MUST produce the exact script bytes generated by [`uip-0003/reference.py`](uip-0003/reference.py):

- 32-byte byte strings use the direct one-byte push length `0x20`;
- integer zero uses `OP_0`;
- integers 1 through 16 use `OP_1` through `OP_16`;
- other integers use minimally encoded CScriptNum bytes and the shortest data push;
- all leaves use Tapscript leaf version `0xc0`;
- semantically equivalent non-minimal encodings are not conforming UIP-3 templates.

## Taproot internal key

Both Payment and Stake outputs MUST use the following BIP 341 NUMS x-coordinate as their Taproot internal key:

```text
50929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0
```

This is the standard BIP 341 point `H = lift_x(sha256(G))`, for which no discrete logarithm is known. Conforming applications MUST use the exact point without adding a hidden random multiple. Security assumes that no party knows its discrete logarithm.

Recipients MUST derive the expected Taproot output key from this internal key and the complete canonical tree and compare it with the actual UTXO. Accepting a sender-provided output key without reconstruction does not establish that no additional spend leaf exists.

## Transaction signatures

All `OP_CHECKSIG` and `OP_CHECKSIGVERIFY` transaction signatures produced for UIP-3 SHOULD use Taproot `SIGHASH_DEFAULT`. Alice and the applicable recipient MUST inspect and agree to the complete transaction before signing. Implementations MUST NOT assume that the claim signature commits to payment amount, fee, or outputs.

## Payment output

The Payment template parameters are:

```text
PaymentTemplate(AlicePubKey, PID)
```

Its Taproot tree contains exactly one leaf: `PaymentLeaf`. The leaf script is:

```text
OP_DUP
OP_SIZE 32 OP_EQUALVERIFY
OP_TOALTSTACK

OP_SWAP
OP_SIZE 32 OP_EQUALVERIFY
OP_SWAP

OP_SWAP
<PID>
OP_CAT
OP_SWAP
OP_CAT

<AlicePubKey>
OP_CHECKSIGFROMSTACK
OP_VERIFY

<AlicePubKey>
OP_CHECKSIGVERIFY

OP_FROMALTSTACK
OP_CHECKSIG
```

The witness elements below are listed from bottom to top, before the tapscript and control block required by BIP 341:

```text
<RecipientTransactionSig>
<AliceTransactionSig>
<AliceClaimSig>
<SID>
<RecipientPubKey>
```

The leaf enforces:

1. `SID` is exactly 32 bytes.
2. `RecipientPubKey` is exactly 32 bytes.
3. `AliceClaimSig` is valid for `SID || PID || RecipientPubKey` under `AlicePubKey`.
4. Alice signed the spending transaction.
5. The claim recipient signed the same spending transaction.

The claim identifies an authorized recipient but does not unilaterally choose the transaction amount. Changing the payment transaction requires a new Alice transaction signature and a recipient signature. This version defines no claim revocation mechanism. Applications that issue replacement payments SHOULD make amounts monotonically increasing, and a recipient MAY choose to broadcast the most favorable fully signed transaction it holds.

## Stake output

The Stake template parameters are:

```text
StakeTemplate(
    AlicePubKey,
    StakeSID,
    Expiry,
    BurnOutput
)
```

`BurnOutputHash` is derived from the complete `BurnOutput` using UIP-2 `OP_OUTPUTHASH` semantics.

The Stake Taproot tree contains exactly two leaves:

```text
Stake root
├── ExpiryLeaf
└── SlashLeaf
```

The branch hash is computed according to BIP 341 by lexicographically sorting the two tapleaf hashes. No additional leaf is permitted.

### Expiry leaf

The expiry leaf is:

```text
<Expiry>
OP_CHECKLOCKTIMEVERIFY
OP_DROP
<AlicePubKey>
OP_CHECKSIG
```

Its witness, from bottom to top, is:

```text
<AliceTransactionSig>
```

`Expiry` is a non-negative minimally encoded CScriptNum accepted by `OP_CHECKLOCKTIMEVERIFY`. The spending transaction MUST satisfy the usual locktime-type and non-final-sequence requirements. After expiry, Alice can recover the Stake output through this leaf.

### Burn output

Version 1 uses the following canonical provably unspendable burn script:

```text
OP_RETURN <0x534c415348>
```

Its serialized scriptPubKey is:

```text
6a05534c415348
```

The five pushed bytes are ASCII `SLASH`. `BurnOutput.amount` is selected by the Stake creator and reviewed by recipients. The burn output is serialized as a complete `CTxOut`, and:

```text
BurnOutputHash = hash_OutputHash(serialize(BurnOutput))
```

### Slash leaf

The Slash leaf is the following exact parameterized program:

```text
<AlicePubKey> OP_TOALTSTACK

OP_SIZE 32 OP_EQUALVERIFY
OP_SWAP
<StakeSID> 6 OP_PICK OP_CAT
2 OP_PICK OP_CAT
OP_FROMALTSTACK OP_DUP OP_TOALTSTACK
OP_CHECKSIGFROMSTACK OP_VERIFY

OP_TOALTSTACK
OP_SIZE 32 OP_EQUALVERIFY
OP_DUP OP_TOALTSTACK
OP_SWAP OP_SIZE 32 OP_EQUALVERIFY OP_SWAP
3 OP_ROLL OP_SWAP
OP_CAT OP_CAT

OP_FROMALTSTACK OP_FROMALTSTACK
OP_2DUP OP_EQUAL OP_NOT OP_VERIFY
OP_2SWAP OP_FROMALTSTACK
OP_CHECKSIGFROMSTACK OP_VERIFY

OP_SWAP OP_DROP OP_CHECKSIGVERIFY

0 OP_OUTPUTHASH <BurnOutputHash> OP_EQUAL
```

The Slash witness elements, from bottom to top, are:

```text
<U1TransactionSig>
<PID>
<Claim2Sig>
<SID2>
<U2>
<Claim1Sig>
<U1>
```

The Slash leaf enforces:

```text
Claim1Message = StakeSID || PID || U1
Claim2Message = SID2      || PID || U2
```

and all of the following conditions:

1. `PID`, `SID2`, `U1`, and `U2` are each exactly 32 bytes where checked by the template.
2. Both claim signatures are valid under the same `AlicePubKey`.
3. Both claims use the one witness-provided `PID`.
4. The first claim uses the `StakeSID` fixed in this Stake leaf.
5. The second claim may use any `SID2`.
6. `U1` and `U2` are different byte strings.
7. `U1` signed the slash transaction.
8. Transaction output zero equals the committed `BurnOutput`.

The signature by `U1` prevents a miner or `U2` from redirecting reporter compensation merely by learning both claims. Outputs after index zero remain unconstrained by the Slash leaf and MAY allocate compensation, change, and fees. Applications SHOULD direct compensation to `U1` and MUST verify that total outputs and fees are economically acceptable before signing.

## Recipient validation

Before accepting an off-chain payment, a recipient MUST independently verify at least:

1. the Stake and Payment outpoints exist and are unspent at the chosen confirmation depth;
2. the exact `AlicePubKey`, `StakeSID`, `PID`, and expiry;
3. the canonical NUMS internal key and complete Taproot tree for both UTXOs;
4. the derived output keys match the on-chain scriptPubKeys;
5. the complete burn output produces the committed `BurnOutputHash`;
6. the burn amount and remaining Stake value satisfy the recipient's risk policy;
7. sufficient time remains before expiry;
8. the Alice claim signature is valid over the exact 96-byte claim message;
9. the proposed payment transaction has the agreed recipient output, amount, and fee;
10. Alice's transaction signature is valid before the recipient adds its own signature.

Confirmation depth, collateral ratio, minimum remaining lifetime, fee policy, and acceptable chain-reorganization risk are application policy, not template constants.

## Interchange data

Applications exchanging a UIP-3 contract MUST provide enough raw data for the recipient to perform the validation above, including:

- Stake and Payment outpoints and complete `CTxOut` values;
- template version;
- `AlicePubKey`, `StakeSID`, `PID`, and expiry;
- complete burn output;
- recipient public key and Alice claim signature;
- proposed payment transaction and Alice transaction signature;
- any chain proof or confirmation information required by recipient policy.

This version does not standardize a network transport, JSON schema, RPC method, or PSBT extension. Applications MUST exchange byte fields losslessly; textual hexadecimal representations SHOULD use lowercase and transaction IDs SHOULD explicitly state display order.

# Rationale

The Stake output is not bound to a predetermined payment recipient. Alice can create it before choosing a recipient. The first conflicting claim is bound to the current Stake through `StakeSID`; the second claim only needs the same `PID` and another user key. This allows evidence learned from a conflicting Payment spend to slash the relevant Stake without requiring every claim to name that Stake.

Only `U1` authorizes the slash transaction. `U2` already obtained or attempted to obtain the conflicting payment and does not need protection from reward theft. Requiring `U1` also prevents a miner that observes both claims from redirecting compensation.

Fixing only output zero allows the burn amount to be guaranteed while leaving compensation and fee outputs selectable when the slash transaction is constructed. The recipient evaluates the committed burn amount and the remaining Stake value before accepting the payment.

# Backward Compatibility

UIP-3 outputs require UIP-2 opcode activation. Before activation, their leaves contain `OP_SUCCESS` bytes and do not enforce the intended conditions. Applications MUST NOT create or accept UIP-3 outputs on a network where UIP-2 is inactive.

Changing any canonical script byte, internal key, tree topology, claim serialization, or witness order creates a different template version and output key. Version 1 applications must reject unknown template versions unless an explicit compatibility mechanism is defined.

# Security Considerations

This protocol provides economic deterrence, not cryptographic prevention of conflicting claims. A recipient must choose collateral and lifetime thresholds appropriate to the payment value and expected confirmation environment.

There is no version-1 claim revocation mechanism. A valid older fully signed payment transaction may remain exercisable. Monotonic amount updates reduce ambiguity but do not revoke earlier transactions.

The claim message has no embedded domain tag. Reuse of `AlicePubKey` in another protocol can enable cross-protocol signature interpretation. A dedicated UIP-3 version 1 key is mandatory.

Claim disclosure can enable slashing when a conflicting claim exists. Applications must protect claim confidentiality consistent with their threat model, while recipients must retain claims and transaction data required to enforce their rights.

The NUMS internal key prevents ordinary key-path spending only under the discrete-log assumption. Recipients must reconstruct the canonical output key rather than trust sender-supplied tree data.

Approaching expiry reduces the time available to detect a conflicting spend and confirm a slash transaction. Fee spikes, censorship, replacement, and chain reorganizations can further reduce effective enforcement time.

Anyone can construct later slash outputs, but only `U1` can authorize the slash transaction. `U1` must ensure the fixed burn output remains at index zero and inspect all other outputs before signing.

# Reference Implementation

Canonical template construction is implemented in [`uip-0003/reference.py`](uip-0003/reference.py). Its self-test checks output serialization, hash construction, fixed-width claim messages, and exact equality with the checked-in template vectors. It does not execute Script or validate transaction signatures.

# Test Vectors

[`uip-0003/template-test-vectors.json`](uip-0003/template-test-vectors.json) contains canonical script bytes, tapleaf hashes, the Stake merkle root, claim messages, signatures, and witness ordering. It is deterministically generated by:

```text
python uip-0003/reference.py --dump
```
