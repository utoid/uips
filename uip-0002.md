# Abstract

This proposal defines a set of four Tapscript extension opcodes for Utocoin: `OP_CAT`, `OP_CHECKSIGFROMSTACK`, `OP_TEMPLATEHASH`, and `OP_OUTPUTHASH`. The first three adopt specified behavior from Bitcoin BIP 347, Bitcoin BIP 348, and Bitcoin BIP 446. `OP_OUTPUTHASH` is a Utocoin-specific primitive that commits to one selected transaction output.

The four opcodes form one activation unit. Before activation they retain their Tapscript `OP_SUCCESS` behavior. Their meaning outside Tapscript is unchanged or invalid as specified below.

# Motivation

Tapscript cannot natively concatenate stack elements, verify signatures over stack-provided messages, or inspect a commitment to the spending transaction. These limitations make many non-interactive contracts require pre-signed transactions or application-specific consensus features.

This opcode set provides small, general primitives. `OP_CAT` builds fixed-format messages, `OP_CHECKSIGFROMSTACK` verifies authorization over those messages, `OP_TEMPLATEHASH` commits to the spending transaction template, and `OP_OUTPUTHASH` constrains one output while leaving other outputs available for fees, rewards, or change.

# Specification

## Terminology and notation

`x || y` denotes byte concatenation with `x` before `y`. Stack diagrams list the top stack item on the right. `hash_tag(x)` denotes the BIP 340 tagged SHA-256 construction:

```text
tag_hash = SHA256(UTF8(tag))
hash_tag(x) = SHA256(tag_hash || tag_hash || x)
```

All four opcodes are defined only while evaluating a Taproot script-path spend using Tapscript leaf version `0xc0`.

## Opcode assignments

| Opcode | Decimal | Hex | Previous Tapscript meaning |
|---|---:|---:|---|
| `OP_CAT` | 126 | `0x7e` | `OP_SUCCESS126` |
| `OP_CHECKSIGFROMSTACK` | 204 | `0xcc` | `OP_SUCCESS204` |
| `OP_TEMPLATEHASH` | 206 | `0xce` | `OP_SUCCESS206` |
| `OP_OUTPUTHASH` | 207 | `0xcf` | `OP_SUCCESS207` |

## Common activation behavior

Before this opcode set is active, encountering any of the four opcode bytes in Tapscript makes the script unconditionally succeed according to the pre-existing `OP_SUCCESS` rules. Relay policy MAY discourage such spends before activation.

After activation, the interpreter MUST execute the semantics below. Defining their behavior restricts transactions that previously succeeded through `OP_SUCCESS`; activation is therefore a soft fork.

## OP_CAT

Stack behavior:

```text
x1 x2 -> x1||x2
```

`OP_CAT` pops the top two stack elements, concatenates them in stack order, and pushes the result. It fails with an invalid-stack-operation error if fewer than two elements exist. It fails with a push-size error if the result would exceed the 520-byte maximum script-element size.

An empty element is permitted. `OP_CAT` remains a disabled opcode in legacy Script and SegWit v0 Script.

This behavior adopts Bitcoin BIP 347.

## OP_CHECKSIGFROMSTACK

Stack behavior:

```text
signature message public_key -> result
```

The public key is the top element, the message is the second element, and the signature is the third element. All three are popped.

The operation then applies the following rules in order:

1. Fewer than three stack elements fails with an invalid-stack-operation error.
2. A zero-length public key fails with a public-key-type error.
3. For a 32-byte public key:
   - an empty signature pushes false;
   - a non-empty signature MUST be exactly 64 bytes;
   - the signature is verified as a BIP 340 Schnorr signature directly over `message`, without first hashing or otherwise transforming the message;
   - an invalid non-empty signature terminates script execution with failure;
   - a valid signature pushes true.
4. A non-empty public key whose length is not 32 bytes is an unknown future public-key type. A non-empty signature is considered successful unless policy discourages unknown public-key types. An empty signature pushes false.
5. Each non-empty signature that reaches verification or unknown-key success consumes the same Tapscript validation-weight budget as a successful Tapscript signature operation.

The message may have any length permitted for a Tapscript stack element. There is no `OP_CHECKSIGFROMSTACKVERIFY`; verify behavior is composed with `OP_VERIFY`.

This behavior adopts Bitcoin BIP 348. Existing Utocoin `OP_CHECKDATSIG` and `OP_CHECKDATSIGVERIFY` behavior is not changed by this proposal.

## OP_TEMPLATEHASH

Stack behavior:

```text
<empty> -> template_hash
```

`OP_TEMPLATEHASH` pushes a 32-byte tagged hash using the tag `TemplateHash`. Its preimage is the concatenation of:

```text
nVersion        int32 little-endian
nLockTime       uint32 little-endian
sha_sequences   32 bytes
sha_outputs     32 bytes
annex_present   uint8 (0 or 1)
input_index     uint32 little-endian
[sha_annex]     32 bytes, present only when annex_present is 1
```

`sha_sequences` is the untagged SHA-256 of the concatenation of every input sequence serialized as a four-byte little-endian integer. `sha_outputs` is the untagged SHA-256 of the concatenation of all outputs serialized in `CTxOut` format. `sha_annex` is defined by Bitcoin BIP 341.

The resulting value is:

```text
hash_TemplateHash(
    nVersion ||
    nLockTime ||
    sha_sequences ||
    sha_outputs ||
    annex_present ||
    input_index ||
    optional_sha_annex
)
```

This behavior adopts Bitcoin BIP 446.

## OP_OUTPUTHASH

Stack behavior:

```text
output_index -> output_hash
```

`output_index` is interpreted as a minimally encoded Script number. It is zero-based and MUST satisfy:

```text
0 <= output_index < transaction_output_count
```

A missing, negative, non-minimal, numerically invalid, or out-of-range index causes script failure. A valid index is popped and replaced by:

```text
hash_OutputHash(serialize(tx.vout[output_index]))
```

The tag is the UTF-8 string `OutputHash`. `CTxOut` serialization is:

```text
amount              int64 little-endian
script_length       CompactSize
scriptPubKey        script_length bytes
```

The hash commits only to the selected output's amount and `scriptPubKey`. It does not commit to:

- the output index itself;
- the number of outputs;
- any other output;
- transaction version or locktime;
- inputs, prevouts, amounts spent, scriptPubKeys spent, or sequences;
- the current input index;
- a Taproot annex.

The script chooses the committed position by supplying `output_index`. Consequently, identical outputs at different positions have identical `OP_OUTPUTHASH` values, but a script checking index `i` still constrains position `i`.

Multiple invocations MAY constrain any desired set of output positions. `OP_OUTPUTHASH` does not compare the result; equality or other processing is composed using existing Script operations.

## Behavior outside Tapscript

`OP_CAT` retains its disabled-opcode behavior in legacy Script and SegWit v0. `OP_CHECKSIGFROMSTACK`, `OP_TEMPLATEHASH`, and `OP_OUTPUTHASH` are invalid opcodes outside Tapscript. No key-path Taproot behavior changes.

# Deployment Profile

This Draft records a test deployment profile that groups the four opcodes in a deployment named `tapscriptextensions`, using versionbits bit 3:

- regtest is always active;
- all non-regtest networks are configured as never active;
- no production-network activation is proposed by this document version.

A future production deployment SHOULD be specified separately so opcode semantics can stabilize independently of activation parameters.

# Rationale

The set is deployed together because its initial application requires message construction, stack-signature verification, and output commitments as one coherent capability. Each primitive remains general and does not encode application-specific identifiers or transaction types.

`OP_OUTPUTHASH` complements `OP_TEMPLATEHASH`. The latter commits to the full output vector and selected transaction context. The former intentionally commits to one `CTxOut`, permitting other outputs to be selected at spend time for rewards, fees, change, or unrelated recipients.

Returning hashes rather than performing an implicit comparison makes both commitment operations composable with existing Script operations.

# Backward Compatibility

This proposal redefines Tapscript `OP_SUCCESS` operations and therefore only tightens validation rules. Blocks valid under these rules were valid to pre-activation nodes, while some spends accepted unconditionally by pre-activation nodes become invalid after activation.

Wallets and applications MUST NOT create outputs relying on post-activation semantics until the intended network reports the deployment active.

# Security Considerations

`OP_CAT` does not increase the 520-byte element limit. Implementations must check the combined size before concatenation.

`OP_CHECKSIGFROMSTACK` verifies exactly the provided message bytes. Protocols are responsible for unambiguous serialization and domain separation. Reusing signing keys across protocols without an enforced domain can permit cross-protocol signature reuse.

`OP_TEMPLATEHASH` and `OP_OUTPUTHASH` commit only to their specified fields. Contract designers must not assume a commitment to omitted inputs, amounts, outputs, annexes, fees, or indexes. In particular, `OP_OUTPUTHASH` alone does not constrain the total output value or transaction fee.

Implementations should precompute individual output hashes or otherwise prevent repeated hashing from introducing unreasonable validation cost.
